  LangGraph state

  class AgentState(TypedDict):
      # this turn only (reset every turn)
      user_input: str
      parsed: ParsedInput | None        # intent, fields, project_ref, choice
      response: str
      # remembered across turns
      draft: dict | None                # half-built project
      awaiting: Literal["fields", "which_project"] | None
      pending_op: dict | None           # e.g. {"op": "update", "changes": 
  {...}, "candidates": ["P-001","P-004"]}

  ParsedInput is what the LLM returns, using structured output (the model fills
  a fixed form instead of writing free text):
  intent ∈ {create, provide_info, list, get, update, delete, choose, cancel, 
  help, unclear}, plus the optional fields fields, project_ref and choice.

  Node flow

  START → parse_input ──route──┬─ create / provide_info ─→ merge_draft → 
  check_required ─┬─ missing → ask_missing → finalize
                               │                                                
           └─ complete → save_project → finalize
                               ├─ list ─────────────────→ list_projects 
  ──────────────────────────────→ finalize
                               ├─ get/update/delete ────→ resolve_project ─┬─ 0 
  matches → not_found ───→ finalize
                               │                                           ├─ 2+
  matches → ask_which ──→ finalize
                               │                                           └─ 1 
  match → do_get/do_update/do_delete → finalize
                               ├─ choose (answer to "which one?") → 
  resolve_project (from candidates)
                               ├─ cancel ───────────────→ clear_pending 
  ──────────────────────────────→ finalize
                               └─ unclear / help ───────→ clarify 
  ────────────────────────────────────→ finalize
  finalize → END     (adds the "you still have an unfinished draft" reminder 
  when needed, per 2b)

  How multi-turn slot filling works

  - Each user line is one graph run. A checkpointer saves the state between
    runs: it's LangGraph's built-in memory, and we use one fixed thread_id.
    That's how the draft survives from one turn to the next.
  - parse_input gives the LLM the current draft and awaiting value. So when the
    app has just asked for the customer and the user types "Acme", the LLM can
    classify it as provide_info with customer="Acme".
  - merge_draft adds the new fields to the draft without wiping existing ones.
    check_required looks for project_name and customer using plain code, not the
    LLM, so it can't be talked out of the rule.
  - Fixed words like quit/exit (handled in cli.py) and cancel are matched
    exactly before the LLM is called. They work even if the API is down.

  Example:
  > new project for the Bangkok office starting Dec 1
    Got it. What's the project name, and who is the customer?
  > it's called Office Fit-out
    Thanks. Who is the customer?
  > list projects
    No projects yet.
    (You have an unfinished draft "Office Fit-out", still missing: customer. 
  Reply with it or type cancel.)
  > Siam Corp
    Saved P-001 "Office Fit-out" for Siam Corp (start 2026-12-01, Bangkok).

  Phase 3: Plain explanation

  The app is a chat in the terminal. You type normal sentences like "add a
  project for Acme". It works out what you want, asks for anything missing, and
  stores projects in a file.

  Three terms you'll see:
  - LangGraph graph: a flowchart written in code. Each box (a node) does one
    job, like "read the sentence" or "save the project". Arrows (edges) decide
    which box runs next. Example: if the sentence was "list projects", the arrow
    goes to the list_projects box.
  - State: the notepad passed between boxes. Example: draft = {"project_name": 
    "Office Fit-out"} sits on the notepad until the customer arrives.
  - Checkpointer: saves the notepad after each of your messages, so the next
    message picks up where you left off.

  First we build the file storage and test it without any AI. Then we connect
  the AI, but only to turn a sentence into a filled-in form. Then we build the
  flowchart that acts on that form. The rules ("customer is required") live in
  plain code, not in the AI. Finally we wrap it in the input loop and test it on
  messy input. At the end you can run pytest (all green, works offline) and
  python main.py for a real chat.

  Phase 4: Options

  The main design choice is how the graph waits for the user's next answer.

  Option: A. One graph run per message + checkpointer
  What it means in practice: Each line you type runs the graph once. The draft
    is remembered in saved state.
  Pros: Every message is read fresh, which is exactly what 2b needs. Simple to
    test turn by turn. Common LangGraph pattern.
  Cons / tradeoffs: The parser needs the draft as context so it can read
    "Acme" as an answer
  Effort: M
  Risk: Low
  ────────────────────────────────────────
  Option: B. Pause/resume with interrupt()
  What it means in practice: The graph stops in the middle at "ask customer"
    and continues when you answer.
  Pros: Feels natural for strict question-and-answer
  Cons / tradeoffs: Doesn't fit 2b: every reply needs routing anyway, so
    pausing adds complexity. Harder to test.
  Effort: M–L
  Risk: Med
  ────────────────────────────────────────
  Option: C. Plain Python state machine, LLM for parsing only
  What it means in practice: No LangGraph, just if statements
  Pros: Least code
  Cons / tradeoffs: Breaks your stated requirement to use LangGraph
  Effort: S
  Risk: Low (but off-spec)

  Recommendation

  Choose Option A. Your answer 2b means every reply can be either an answer or a
  new command, so every reply has to be parsed and routed anyway. A does that
  naturally. It also makes the offline tests from 3a simple: feed in a scripted
  message, check the reply and the saved state. If you later decide you want
  strict mode (2a), Option B becomes reasonable.

  langchain-openrouter, but it's still version 0.x. ChatOpenAI with
  base_url="https://openrouter.ai/api/v1" is the well-tested route, so I'll keep
  that. The default way of getting structured output has changed between
  versions, so I'll set it explicitly: with_structured_output(ParsedInput, 
  method="json_schema", strict=True, include_raw=True). The include_raw=True
  part makes a bad reply come back as an error value instead of crashing, so it
  can go to the unclear path. (LangChain OpenRouter docs, OpenRouter blog guide,
  OpenRouter structured outputs, ChatOpenAI.with_structured_output reference)

  5. The model is fine. OpenRouter's live model list shows openai/gpt-4o-mini
  still available. It supports structured output and tool calling, and costs
  about $0.15 per million input tokens and $0.60 per million output tokens.

  with one .env line. The README will say so.

  requirements.txt, explicit structured-output settings, and every optional
  field in ParsedInput written as str | None with no default value. The last one
  is because strict mode rejects schemas with default values.

  Why it happens
